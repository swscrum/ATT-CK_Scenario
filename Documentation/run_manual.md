# Run manual

How to bring the lab up, run the attack chain, and where the resulting logs
land for SIEM ingestion. Network topology, service descriptions, and the
`db-internal` credential set are documented in the [README](../README.md);
this manual only covers what the README doesn't: orchestrator flags, chain
steps, and the full log inventory.

## Prerequisites

Docker and the Compose plugin. `cd Infrastructure` before any `docker
compose` command — all paths in `docker-compose.yml` (bind mounts, build
contexts) are relative to that directory. `tools/run.sh` does this `cd`
itself, so it can be invoked from the repo root. First run after a clone (or
after a `git pull` that touched a Dockerfile or seeded file) needs an image
build; every run after that reuses the cached layers.

## Pre-run checklist

Run through this before every scenario, especially `--mode advanced` or `--pacing realistic`.

### 1 — Tear down any previous lab instance

```bash
cd Infrastructure && docker compose down
```

Leftover containers from a prior run carry stale Sliver sessions and open ports.
Skip if you are certain no lab is running (`docker ps` shows no lab containers).

### 2 — Build images

**Normal case** (first clone, or after a Dockerfile / seed-data change):

```bash
cd Infrastructure && docker compose build
```

Uses layer cache — fast if nothing changed. Always safe to run.

**Apache SSL cert missing** (symptom: apache crash-loops with `server.crt: No such file or
directory` in `docker logs apache`):

```bash
cd Infrastructure && docker compose build --no-cache apache
```

The cert is generated by `openssl req` inside the Dockerfile. A stale cached layer
skips that step and the container starts without a cert. `--no-cache` forces
regeneration. Do NOT add `--no-pull` — that flag does not exist in the Compose
version used here.

**Kali image — advanced mode only** (`--mode advanced`):

The Sliver session and beacon implants are compiled and baked into the kali image at
build time (`RUN sliver-server daemon ... && sliver-client --rc ...`). This takes
approximately 3 minutes on the first build after a clean pull. Subsequent builds
reuse the cached layer. If kali's Dockerfile or `advanced_initial_access.py`
changes the LHOST/LPORT (`10.10.0.2:8080`), force a rebuild:

```bash
cd Infrastructure && docker compose build kali
```

**Noise containers** (`noise_*`):

Noise containers use `python:3.12-alpine` from Docker Hub. Only rebuild them if their
Dockerfile or scripts changed. If Docker Hub is unreachable, skip them explicitly:

```bash
cd Infrastructure && docker compose build kali apache ubuntu_workstation vinzenz_ws luke_ws db-internal router
```

### 3 — Verify host ports are free

| Port | Container |
|---|---|
| 80 | `apache` |
| 5901 | `ubuntu_workstation` (VNC) |

```bash
ss -tlnp | grep -E ':(80|5901) '
```

Kill any conflicting process or `docker compose down` a stale project before continuing.

### 4 — Run

```bash
# Basic chain, default pacing:
tools/run.sh --mode basic

# Advanced chain (Sliver-based, full 10-step chain):
tools/run.sh --mode advanced

# Realistic pacing (stretches inter-step timing into an 8-hour synthetic workday,
# enables noise containers — available after branch 83-add-more-realistic-logging-methods
# is merged):
tools/run.sh --pacing realistic --mode advanced
```

## Quickstart

1. `cd Infrastructure && docker compose build`
2. `cd .. && tools/run.sh` — brings the lab up, runs the basic chain, snapshots logs, tears down
3. `cat Attack-chain/results/run-*/chain-*.json` — per-step ground truth for the run just finished
4. `ls Infrastructure/logs/run-*Z/` — apache/router/workstation log snapshot from that run
5. `tools/run.sh --keep-up` — rerun without teardown, e.g. to inspect a live container before tearing it down with `docker compose down`

## Two ways to run

`tools/run.sh` is the default path: it brings the lab up, runs `main.py`
inside `kali` with whatever arguments you pass through, snapshots
apache/router/workstation logs into `Infrastructure/logs/run-<ISO8601>Z/`,
then tears the lab down. Use it for anything you'd report on or hand to a
SIEM demo, since it's the only path that produces that snapshot directory.

Run `main.py` directly via `docker compose exec kali python3
/Attack-chain/main.py ...` when the lab is already up and you're iterating
on a single step — no snapshot, no teardown, faster turnaround.

## Flag reference

### `tools/run.sh`

| Flag | Effect |
|---|---|
| `--build` | `docker compose up -d --build` instead of plain `up -d` — use after a Dockerfile or seed-data change |
| `--keep-up` | Skip `docker compose down` after the run; tear down later yourself |

Any other argument is forwarded verbatim to `main.py`.

### `Attack-chain/main.py`

| Flag | Effect |
|---|---|
| `--mode {basic,advanced}` | Aliases `b`/`basic`, `a`/`adv`/`advanced`. Default `basic`. |
| `--only <step>` | Run a single step. Mutually exclusive with `--from`/`--to`. |
| `--from <step> --to <step>` | Run an inclusive range of the chain. |
| `--no-linpeas` | Skip the LinPEAS drop, use targeted enumeration commands only. Default: LinPEAS enabled. |
| `--target` | Recon/exploit target host. Default `router`. |
| `--results-dir` | Default `/Attack-chain/results` (inside `kali`). |
| `--kali-host` | Default `10.10.0.2`. |
| `--wordlist` | Gobuster wordlist. Default `/usr/share/wordlists/dirb/common.txt`. |
| `--list` | Print the configured steps for `--mode` and exit. |
| `-v` / `--verbose` | Debug-level orchestrator logging. |

State produced by one step (a shell handle, a Sliver session ID, ...) lives
only in the running process's memory. `--only` or `--from` on a step that
isn't first in the chain raises `missing required state` unless you've just
run the earlier steps in the same `main.py` invocation — there is no
resume-from-disk.

## Logs

| Path | Format | Ingest for |
|---|---|---|
| `Infrastructure/logs/apache/access.log`, `error.log`, `forensic_log` | Apache combined / error / forensic | `recon` (404 probe noise), `exploit` (CVE-2021-42013 traversal URI — T1190); `forensic_log` pairs `+id`/`-id` per request and captures truncated/aborted requests that never get a normal `access.log` line (useful for failed CVE-2021-41773 attempts) |
| `Infrastructure/logs/workstation/auth.log` | rsyslog ISO; sshd default `INFO` on `ubuntu_workstation` (no key fingerprint) | `Accepted publickey` for `john.stravidis` on `ubuntu_workstation` (T1021.004) |
| `Infrastructure/logs/luke_ws/auth.log`, `Infrastructure/logs/vinzenz_ws/auth.log` | rsyslog ISO; sshd `LogLevel VERBOSE` on `luke_ws` and `vinzenz_ws` (key fingerprint logged) | `Failed password` entries from the `lateral` credential-stuffing pass (T1110.004) |
| `Infrastructure/logs/db/postgresql-YYYY-MM-DD.log` | Postgres, `log_statement=all`, prefix `%t [%p]: [%l-1] user=%u,db=%d,app=%a,client=%h` | every connect/disconnect and query against `waystar`, including the `pg_dump` exfil (T1213, T1041) |
| `Infrastructure/logs/attacker/attack_steps_<run_id>.log` | syslog-style key=value, three event types per step: `event_type=phase_start step=<name> tactic_id=<TA####> tactic="..." techniques="T1,T2"`, `event_type=cmd_exec step=<name> tactic_id=<TA####> techniques="..." cmd="..."`, `event_type=phase_end step=<name> tactic_id=<TA####> ok=true\|false elapsed=<sec>` | attacker-POV ground truth; correlate by `run_id` and `step` against defender logs; filter by `event_type` to separate phase boundaries from individual commands |
| `Attack-chain/results/run-<run_id>/chain-<run_id>.json` | JSON, per step: `started`/`ended`/tactic/techniques/ok/elapsed | master timeline for matching SIEM alerts to chain steps |

`router` has no compose volume mount — its `/var/log` only reaches the host
via `tools/run.sh`'s teardown snapshot into
`Infrastructure/logs/run-<ISO8601>Z/router/`, alongside a duplicate copy of
the apache and workstation logs and `docker logs` stdout/stderr for `apache`,
`router`, `ubuntu_workstation`, and `kali`. Running `main.py` directly
without `run.sh` means router activity is only visible via `docker logs
router` or `docker exec router cat /var/log/...` while the container is
still up.

### Splunk ingestion (TA)

A minimal Splunk Technology Add-on lives in `Infrastructure/splunk/`. Drop the
contents into `$SPLUNK_HOME/etc/apps/cyberlab_ta/` on your Splunk instance and
restart Splunk.

**`default/inputs.conf`** — monitor stanzas pointing at `/opt/logs` (bind-mount
the lab's `Infrastructure/logs/` directory there on the Splunk host):

```
[monitor:///opt/logs/attacker/attack_steps_*.log]  sourcetype=attacker_chain
[monitor:///opt/logs/apache/access.log]            sourcetype=access_combined
[monitor:///opt/logs/apache/auth.log]              sourcetype=linux_secure
[monitor:///opt/logs/workstation/auth.log]         sourcetype=linux_secure
[monitor:///opt/logs/vinzenz_ws/auth.log]          sourcetype=linux_secure
[monitor:///opt/logs/luke_ws/auth.log]             sourcetype=linux_secure
[monitor:///opt/logs/*/lab-fim.log]                sourcetype=lab_fim
[monitor:///opt/logs/router/ulog-iptables.log]     sourcetype=ulog_iptables
[monitor:///opt/logs/db/postgresql-*.log]          sourcetype=postgresql
```

**`default/props.conf`** — timestamp and KV extraction config per sourcetype:

| Sourcetype | Timestamp format | KV extraction |
|---|---|---|
| `attacker_chain` | `%Y-%m-%dT%H:%M:%S.%6N%:z` | `REPORT-attacker_chain_fields` via transforms |
| `lab_fim` | `%Y-%m-%dT%H:%M:%S%z` | `REPORT-lab_fim_fields` via transforms |
| `linux_secure` | `%Y-%m-%dT%H:%M:%S.%6N%:z` | default syslog parsing |
| `ulog_iptables` | `DATETIME_CONFIG = CURRENT` | — |
| `postgresql` | `%Y-%m-%d %H:%M:%S %Z` | — |

**`default/transforms.conf`** — regex field extractions:

| Transform | Regex | Used by |
|---|---|---|
| `attacker_chain_kv` | `(\w+)=(?:"([^"]*)"\|(\S+))` | `attacker_chain` — extracts `event_type`, `step`, `tactic_id`, `techniques`, `cmd`, `ok`, `elapsed` |
| `lab_fim_kv` | `(\w+)=(\S+)` | `lab_fim` — extracts `tag`, `host`, `path`, `event` |

**Key Splunk searches after a run:**

```spl
index=cyberlab sourcetype=attacker_chain event_type=phase_start | table _time step tactic_id techniques
index=cyberlab sourcetype=attacker_chain event_type=cmd_exec step=advanced_exfiltration | table _time cmd
index=cyberlab sourcetype=linux_secure "Accepted publickey" | table _time host user
index=cyberlab sourcetype=postgresql | search "SELECT" | table _time user db message
```

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `docker compose exec kali` fails right after `tools/run.sh` starts, or the chain errors on a missing tool/file | Images built before a Dockerfile/seed-data change, so `up -d` reused stale layers | `tools/run.sh --build` |
| `missing required state: [...]` on `--only <step>` or `--from <step>` | The step needs state (`www_shell`, `root_shell`, ...) that only exists in the same process after running the earlier steps — nothing is resumed from disk | Run the chain from `recon` (or whichever step actually produces the missing key) in the same invocation |
| `--only X` combined with `--to Y` errors with "cannot be combined" | `--only` and `--from`/`--to` are mutually exclusive in `argparse` | Use either `--only <step>` or `--from <step> --to <step>` |
| Host port 5901 or 80 already bound | Another compose project, or a previous lab instance, still has the port | `docker compose down` the conflicting project, or check `docker ps` for a stray container |
| `Infrastructure/logs/attacker/` missing after a fresh clone | The directory is gitignored and only created on first `attacklog.open_log()` call, i.e. the first chain run | Run the chain once; the directory and `.log`/`.md` files appear afterward |
| Workstation/luke/vinzenz containers unreachable by hostname from inside another container | `apache` lives in `dmz_net`, so Docker's embedded DNS doesn't resolve it from `internal_net` hosts — they're pinned via `extra_hosts` in `docker-compose.yml` instead | Don't rely on DNS for `apache` from internal hosts; use the pinned IP or the existing `extra_hosts` entry |
| `apache` crash-loops; `docker logs apache` shows `server.crt: No such file or directory` | The apache image is stale — the `openssl req` build step was skipped because a cached layer was reused | `cd Infrastructure && docker compose build --no-cache apache` (do not add `--no-pull` — that flag does not exist here) |
| `tools/run.sh --mode advanced` exploit step hangs or Sliver session never arrives | Kali image was rebuilt without the baked implants, or the image predates the implant-bake layer | `cd Infrastructure && docker compose build kali`; the `RUN sliver-server ...` layer takes ~3 min on first compile |
| `docker compose build` fails on noise containers with a TLS timeout | `python:3.12-alpine` not cached locally and Docker Hub unreachable | Build only the services that changed: `docker compose build kali apache ubuntu_workstation vinzenz_ws luke_ws db-internal router` |
| `unrecognized arguments: --pacing realistic` from `main.py` | `--pacing` is not implemented on this branch yet | Remove `--pacing realistic` from the command, or switch to `83-add-more-realistic-logging-methods` |
